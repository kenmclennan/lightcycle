# Measuring TUI performance

`lc tui` polls `LightcycleApp._refresh()` every `POLL_INTERVAL_SECONDS` (10s, `app.py:69`). This document is the method for finding out where a tick's time and memory go, and this item's own measurement run against it.

## Two tools, two questions

**`py-spy`** (sampling, attaches to a running `lc tui` process by PID, ~1% overhead, no code changes) answers "where does wall-clock time go" - it finds slow code.

```
pgrep -f "lightcycle.*tui"
py-spy record -o tui.svg --pid <pid> --duration <seconds>
```

Add `--idle` to include idle/await time in the flame graph. Textual is asyncio - `_refresh()` spends most of its life awaiting the event loop between ticks, so an idle-excluded chart under-represents wall time and an idle-included chart can be misread as "working" when it is actually "awaiting". State in any write-up which was used.

**`cProfile`** (deterministic, stdlib, distorting) answers "how many times was this called" - it finds repeated code, the [[LC-520]] bug class this item is chasing the residue of.

```
python -m cProfile -o /tmp/tui.prof -m lightcycle tui
python -m pstats /tmp/tui.prof
```

Inside `pstats`, `sort ncalls` then `stats N` - never `sort cumulative` for this question, since cProfile's own overhead distorts absolute timings and only call counts are trustworthy.

Capture **many ticks, not one**. A 30-second `py-spy` capture gives three ticks at the real 10s interval; prefer minutes, to see a steady state rather than one sample.

## The counter

A lightweight, config-gated counter records each `_refresh()`'s wall duration and the process's own RSS, appended to the existing run log - no profiler, no code path change, near-zero cost when off.

Turn it on with `tui-metrics: true` in `~/.lightcycle/config`, or `LC_TUI_METRICS=true`. Samples land in `<data_root>/logs/run.log` - `~/.lightcycle/logs/run.log` by default (`config.py`'s `data_root()`/`default_data_root()`). Each line:

```
10:20:29  tui      wall_ms=79 rss_kb=82384
```

`wall_ms` is `_refresh()`'s own wall-clock duration in milliseconds; `rss_kb` is the process's RSS in kilobytes at the end of that tick, or `?` when it could not be read.

## Contention and the memory gate

Before recording a figure taken with the pool at `max-agents`, check `lc config`'s current `memory-reserve-fraction`/`suspend-pressure`/`resume-pressure` values and state here whether [[LC-506]]'s admission/suspension gate was active or neutered on the machine the measurement was taken on - the brief recorded it neutered (`memory-reserve-fraction: 0`, `suspend-pressure: 0.99`) as of 2026-09-15; this can change, so record what was actually true at measurement time, not what a past write-up said.

## Results (this item's measurement run, 2026-09-15)

**Setup.** The store snapshot used for this run is a point-in-time copy of this machine's own live `~/.lightcycle/store.db` (113 real nodes, taken via `sqlite3 .backup` so the live database was never opened for writing) plus a copy of `~/.lightcycle/workflows`, loaded from an isolated `LC_HOME` - the live store itself was never pointed at directly. This gives production-shaped data (real item/step counts and structure) without the risk of a live-store test run. `_refresh()` was driven directly (`LightcycleApp._refresh()` under Textual's `run_test()` harness, the same call `session.run(session.app._refresh)` makes in the test suite) rather than through a real interactive terminal session, because the profiling and counter code paths are identical either way and this removes the need for a pty. `tui-metrics: true` was set for the whole run, so every figure below came from the shipped counter, not a one-off instrument.

**The memory gate, checked at measurement time.** `~/.lightcycle/config` on this machine currently reads `memory-reserve-fraction: 0`, `suspend-pressure: 0.99`, `resume-pressure: 0.70` - confirmed neutered, matching the brief's 2026-09-15 record. No real agent pool was started for this run (spinning real `claude`-backed workers to generate genuine CPU/memory contention is a cost and blast-radius call beyond what this measurement pass makes on its own); the figures below characterise a single `lc tui` process's steady-state tick, not pool contention. A contention measurement remains open for whoever next runs this method with a live pool.

**Steady-state wall-clock.** 57 real ticks recorded by the counter across this run (18 + 8 + a handful from setup verification, all against the same 113-node snapshot): `wall_ms` ranged 57-124, mean ~83ms. This is markedly higher than [[LC-520]]'s stale ~140ms-total/~115ms-`DoneUseCase` figures would suggest for a store this size, which is explained by the cProfile finding below - `DoneUseCase` was not, in fact, fully fixed by LC-520.

**RSS trend.** `rss_kb` rose from ~73-80MB over the first several ticks (process/import/cache warm-up) to a plateau around 88-89MB for the remainder of the run. No unbounded growth was observed over this run's length; a longer session (the brief's own "does memory grow over a long-running session" question) is not settled by 57 ticks over a few minutes and remains open.

**cProfile call-count finding.** Sorted by `ncalls` over an 8-tick cProfile run: `sqlite_store.py:608 _row_to_step` was called 40,167 times - roughly 2,200+ times per `_refresh()` tick, against a store of 113 nodes. Tracing callers: `done.py:61 _closed_items` (inside `DoneUseCase.execute()`, called once per tick from `_refresh_done_view`) drives `_rows_to_items`, which calls `_child_states_of` once per closed item (14 times/tick in this run) - and `_child_states_of` itself makes a `_row_to_step` call per child, repeated in full on every tick regardless of whether anything changed. `DoneUseCase.execute()` alone accounted for ~51% of a tick's total time in this profile (0.503s of 0.986s cumulative, across the 9 `_refresh()` calls this profile captured). This is the same call-count-explosion shape [[LC-520]] fixed in `get_item`, recurring in a different path (`DoneUseCase`/`_closed_items`/`_child_states_of`) that LC-520 did not touch. Not fixed here - recording it for [[LC-705]], per this item's own out-of-scope (below).

**`py-spy` in this environment.** `py-spy record --pid <pid>` requires root on macOS (`task_for_pid` is SIP-gated) and this measurement pass had no interactive path to grant it, so no flame graph was captured here. The commands above are runnable and unchanged by this; the deterministic `sort cumulative` view from the same cProfile run (not shown, since cProfile's own overhead distorts absolute time) corroborated `DoneUseCase.execute()` as the largest single contributor to a tick, consistent with the call-count finding above.

**Deferred findings.** This spec's own Deferred findings section names two further gaps this measurement run did not need to reprove by profiling - both found by reading `_refresh()`, not sampling it: `_refresh()` runs its full row-derivation work every tick regardless of whether the priority screen is the one on top of the screen stack, and the priority list's row-derivation runs unconditionally every tick even when the shape guard finds nothing changed. Acting on any of the three findings recorded in this document - the `DoneUseCase` call-count finding above, or either of the spec's own Deferred findings - is [[LC-705]]'s scope; this item changes no TUI behaviour beyond the gated counter.

## Results ([[LC-729]]'s measurement run, 2026-09-17)

**Setup.** A fresh point-in-time copy of this machine's own live `~/.lightcycle/store.db`, taken via `sqlite3 .backup` (live store never opened for writing) plus a copy of `~/.lightcycle/workflows`, loaded from an isolated `LC_HOME` - the live store itself was never pointed at directly. The live store had grown again since [[LC-705]]'s run, to 513 items / 2671 steps at measurement time (counted directly on the copied file via `sqlite3`, not through the engine - see the worker-isolation note under Contention below for why). `tui-metrics: true` was set for the counter runs.

**The memory gate, checked at measurement time.** `~/.lightcycle/config` on this machine currently reads `memory-reserve-fraction: 0.65`, `suspend-pressure: 0.40`, `resume-pressure: 0.25`, `max-agents: 5` - meaningfully active, not neutered, unlike [[LC-705]]'s 2026-09-15 snapshot (`memory-reserve-fraction: 0`, `suspend-pressure: 0.99`). Read directly from the config file, not via `lc config` - this write-code pass runs under a worker role, which the CLI's own worker-permission gate does not allow to run `lc config`.

**Steady-state wall-clock and RSS, over a run materially longer than 57 or 720 ticks.** `_refresh()` was driven back-to-back via `TuiSession.poll_tick()` (no artificial delay between calls) against the snapshot above, for 2,000 ticks in ~206s of real compute time. A literal 2-hour, real-time-paced continuous session (the ~720-tick target) was not practical for this pass: this write-code step is a single ephemeral automated agent turn with a bounded compute budget, not a multi-hour interactive session. Substituting tick count for wall-clock duration is a deliberate choice, not an oversight - `_refresh()`'s own cost and CPython's memory/object-retention behaviour are both driven by how many times it is called, not by how much real time elapses between calls, so 2,000 back-to-back ticks (2.8x the ~720-tick target) exercise the "long session" question at least as hard as a spaced-out 2-hour run would, on the axis that actually matters here. A separate ~15-minute real-time-paced session was also attempted directly against a real `lc tui` process (not the harness) to corroborate at real terminal speed; that run is reported separately below because it was contaminated by an operational mistake and answers a narrower question.

`wall_ms`, excluding the first 20 ticks (warm-up): mean ~61ms, p50 53ms, p90 81ms, p99 178ms, occasional outliers up to 437ms. The outliers coincide with this machine genuinely running several other concurrent agents during the measurement window (visible in a real `lc tui`'s own priority list at the time - LC-746, LC-766, LC-738, LC-775 were all mid-flight); they are host contention, not this codebase's own cost, and py-spy/cProfile would not attribute them to `_refresh()` either.

`rss_kb` across the same 2,000 ticks: ~63-69MB for the first 100 ticks (past initial import/mount warm-up), climbing to ~90-96MB by ticks 1,700-2,000 and still rising, not plateaued. **This changes LC-527's own conclusion.** LC-527 observed a plateau around 88-89MB and reported "no unbounded growth... over this run's length", but only ran 57 ticks - long enough to _reach_ roughly the same 88-89MB level this run passes through around tick 900-1,000, not long enough to see that the climb continues past it. Run further to check whether growth is real rather than a measurement artifact: `gc.collect()` forced every 300 ticks across a separate 1,500-tick run neither reduced RSS nor found cyclic garbage (`gc.garbage` stayed empty each time), while `gc.get_objects()`'s own live-object count grew monotonically - 170,612 -> 216,791 -> 262,972 -> 309,143 -> 355,313 across the five checkpoints (~123 new _reachable_ objects retained per tick, not uncollected garbage awaiting a GC pass). A type-count diff between tick 200 and tick 700 of a separate run identifies where: `rich.segment.Segment` (+108/tick), plus exactly +1/tick each of `textual.events.Callback`, `asyncio.locks.Event`, `collections.deque`, `functools.partial`, `builtins.set`, and `textual.widget.PseudoClasses`. This is not either of the two already-known unbounded caches from [[LC-705]]'s Deferred findings (`_done_cost_time_cache`, `_stats_cache`) - both are gated to only populate while their own view is visible, and this harness never switches views - so it is a new deferred finding (below), not a re-confirmation of an old one.

**Explicit answer: yes, RSS grows over a long session**, measurably and past the point LC-527 stopped looking, and the growth traces to reachable objects in the Textual/Rich rendering layer rather than to either named application-level cache.

**Real-terminal corroboration (contaminated - reported for what it can still show).** A real `lc tui` process (not the harness) was also run against the same snapshot for real-time-paced ticks. An earlier attempt at this same run, backgrounded and `disown`ed to survive past its own launching command, was not actually cleaned up when that command finished. It kept running unnoticed for the whole ~15 minutes that a second, deliberate attempt was then run alongside it. The resulting `run.log` interleaves two concurrent processes' samples throughout (visible as paired entries a few seconds apart at nearly every timestamp) with no PID recorded per line to de-multiplex them after the fact. Both strays were eventually found and killed via `pkill -f`, after `ps`/`pgrep` from the driving shell failed to show them at all (only `lsof`/`pkill` could see them - a sandboxing quirk of this environment worth knowing for whoever next tries this). Recorded here as a process-management mistake, not corrected retroactively: across the resulting 260 contaminated samples, `wall_ms` ranged 50-1,318ms (mean ~153ms - both processes competing for the same CPU, plus the same host contention noted above) and `rss_kb` ranged ~50-105MB. This is consistent in order of magnitude with the clean harness run above and confirms real ticks land every ~10s at real terminal speed, but it does **not** independently answer the single-process long-session RSS question - that answer rests on the clean 2,000-tick harness run above, not on this one.

**cProfile call-count finding.** A fresh 8+-tick `cProfile` run (9 ticks captured), against a separate copy of the same live store taken moments later (513 items / 2671 steps - store size did not change meaningfully between the two snapshots), driven the same way as [[LC-705]]'s run (`TuiSession`, sorted `ncalls`, never `cumulative`):

- `_refresh()` cumtime: 0.6263s over 9 ticks.
- `DoneUseCase.execute()` cumtime: 0.3085s - **49.3% of a tick**, up slightly from LC-705's post-fix 48.2%. Of that 0.3085s, 0.2856s (92.6%) is the single `all_items_including_done()` call inside `_closed_items()` - essentially all of what remains of `DoneUseCase`'s cost is exactly the cache-rebuild scan Why's premise expected, not some other, newly-exposed cost.

**`py-spy` in this environment.** Still blocked, for the same reason as LC-527's run: `py-spy` is not even installed in this environment, and attaching to a real PID would additionally require root (`task_for_pid` is SIP-gated on macOS) - `sudo -n true` confirms no passwordless sudo is available to this non-interactive agent, and there is no interactive path to supply a password. **Contention reading against the real live pool: not taken by this pass, structurally.** This write-code step executes from a git worktree checkout. **Recommendation on [[LC-730]]: close it unbuilt.** `DoneUseCase`'s 49.3% share sounds large as a fraction, but in absolute terms it is ~30ms of CPU work once every 10-second tick - well under 1% of a single core - and that fraction barely moved (48.2% -> 49.3%) while the store it scans grew 17% (steps) since LC-705's run, so it is not a cost that compounds quickly on its own. The precedent Design F points to, `_done_cost_time_cache`, does not actually transfer: it caches a per-item _value_ keyed on a fact that cannot change once set (`item.closed_at`), while what LC-730 would need to cache is the _membership_ of the done set itself, which changes on every completion and, per [[LC-746]] (currently `queued`, unresolved as of this writing), on every reopen too - LC-746's items 2 and 4 are exactly the "a reopened item's rolled-up state" edge case a done-set cache would need to invalidate on correctly, and it is a live, currently-open bug in this exact area, not a hypothetical risk. Building a stateful cross-tick cache in a zone whose transition-detection is presently known-buggy, for a saving that is not user-perceptible, is not a good trade. If per-tick cost ever does become a real concern, [[LC-705]]'s own still-open Deferred finding - only running Done/Backlog derivation while their view is actually visible - is the cheaper lever to pull first, and does not carry a cross-tick invalidation problem at all.

## Results ([[LC-781]]'s measurement run, 2026-09-18)

**Setup.** A fresh point-in-time copy of this machine's own live `~/.lightcycle/store.db` (572 items / 3,106 steps, counted directly on the copied file via `sqlite3`), taken via `sqlite3 .backup` (live store never opened for writing), plus a copy of `~/.lightcycle/workflows`, loaded from an isolated `LC_HOME` built with a real `SqliteStore` against the copy (not `FakeStore`) - the live store itself was never pointed at directly, and the copy's `data_root()` differs from the machine's `default_data_root()`, so the LC-13.2 live-store worktree guard does not fire. `_refresh()` was driven directly via `TuiSession.poll_tick()` (no artificial delay), the same mechanism prior runs used. `~/.lightcycle/config` at measurement time: `memory-reserve-fraction: 0.65`, `suspend-pressure: 0.40`, `resume-pressure: 0.25`, `max-agents: 5` - unchanged from [[LC-729]]'s 2026-09-17 snapshot, still meaningfully active, not neutered.

**Correction to LC-729's own six-type finding.** Repeating LC-729's type-count diff on a fresh, careful run - checked both with a forced `gc.collect()` before each sample and, separately, with no forced collection at all, to rule out an uncollected-cycle artifact - only **two** of the six types LC-729 named actually grow: `rich.segment.Segment` and `textual.widget.PseudoClasses`. The other four LC-729 named as growing at a flat +1/tick each - `textual.events.Callback`, `asyncio.locks.Event`, `collections.deque`, `functools.partial` - plus `builtins.set`, show **zero** growth over a clean 700-1,000 tick run in this pass, under either GC condition: `Callback` stayed at 67, `Event` at 152, `deque` at 223, `partial` at 260, `set` at ~2,534-2,535, tick after tick. Referrer traces on live instances of these five show ordinary, static framework/stdlib bookkeeping (a `Pilot` test-harness callback, `threading.Event`/`Condition` internals, `typing`/`sys` module machinery) - nothing tied to this app's own per-tick work. LC-729's own doc already flagged uncertainty about its six-type diff ("does not state whether this was the same 1,500-tick run or a third one") - this pass's own repeat resolves that ambiguity in favour of **two** growing types, not six.

**A materially longer run was attempted and blocked by machine contention, not by this pass's method.** Design B's own target is 20,000 ticks. Two attempts were made (a 20,000-tick run, then a scaled-down 6,000-tick run after the first stalled) against this same snapshot; both stalled after their first few hundred ticks, with the process alive and consuming CPU but RSS flat for minutes at a time - `uptime` during both attempts showed a sustained load average of 29-34 on this machine (`12:02  up 16 days, load averages: 29.22 33.02 23.08`), versus the ~10.5 ticks/second this same script achieved cleanly earlier in this pass. This is the same machine this item's own Why/Sources already flag as having a documented history of contention-driven swapping ([[LC-732]]); this pass adds a second, independent instance of it blocking a measurement outright rather than merely slowing it. This item's own practical B run is therefore **1,000 ticks**, checkpointed every 100 (well inside the "at least every 2,000" acceptance bar, just over a shorter total run) - not the targeted 20,000 - stated plainly per Design B's own allowance for when a longer run isn't practical, rather than silently downgrading the target.

**The clean 1,000-tick trend.** `gc.collect()` forced at every 100-tick checkpoint; `gc.garbage` stayed empty throughout (reachable retention, not uncollected cycles, matching LC-729's own reading). `rss_kb`: 66,704 (tick 100) -> 70,128 -> 71,696 -> 71,680 -> 73,936 -> 75,456 -> 77,536 -> 79,488 -> 81,456 -> 83,632 (tick 1,000). `gc.get_objects()` total: 111,878 -> 246,440 over the same range. Per-100-tick deltas for the two growing types are **exactly constant** across every checkpoint window from tick 200 to tick 1,000: `Segment` +10,800/100 ticks (108.00/tick) at every single window, `PseudoClasses` +100/100 ticks (1.00/tick) at every single window - no deceleration is visible anywhere in the range this pass actually measured. Read plainly, on the evidence directly available from this pass's own run, the marginal growth rate is **holding steady, not decaying** - "unbounded on the evidence available" in Design B's own terms, for this specific 0-1,000 tick window.

**Why a plateau is nonetheless the well-supported prediction beyond this window.** Direct instrumentation of the live `PriorityTable` widget's own Textual-internal caches (not gc-wide counts) shows exactly one of them still filling: `_row_render_cache`, `_line_cache`, and `_row_renderable_cache` (`LRUCache` instances capped at 1,000 each) are already **full** by tick 500. Only `_cell_render_cache` (`LRUCache(10000)`) is still growing at tick 1,000 - measured at 628 entries (tick 100), 3,028 (tick 500), 6,028 (tick 1,000): **exactly +6.0 entries/tick**, constant across both measured windows, 60% of its 10,000 cap. Reading `_data_table.py` (Textual 8.2.8's `widgets` package) explains why this cache never gets a hit across ticks even though the rendered content is often identical: its cache key is `(row_key, column_key, base_style, cursor, hover, self._show_hover_cursor, self._update_count, self._pseudo_class_state)`, and `self._update_count` is a single counter incremented on every `update_cell()` call table-wide (`_data_table.py:906`) while `self._pseudo_class_state` is reassigned to a **freshly constructed** `PseudoClasses` object on every `render_lines()` call (`_data_table.py:2474-2475`, `self._pseudo_class_state = self.get_pseudo_class_state()`) - so every render generation's cache keys are guaranteed distinct from the previous generation's, regardless of content, and the previous generation's entries (and the `PseudoClasses`/`Strip`/`Segment` objects embedded in their keys and values) stay alive until the LRU evicts them. Extrapolating the measured +6.0 entries/tick at zero deceleration predicts `_cell_render_cache` saturates around **tick ~1,662** (`(10000 - 6028) / 6.0 ≈ 662` more ticks past tick 1,000); once saturated, each new entry's insertion evicts exactly one old entry, so the _cache's own size_ - and, on this pass's own reading of the mechanism, therefore the bulk of this growth - should stop increasing at that point. [[LC-729]]'s own already-recorded tick-2,000 endpoint (RSS ~90-96MB, "still climbing") sits almost exactly at this pass's own independently-computed prediction for where the curve should be levelling off, rather than diverging further - consistent with LC-729 having stopped observing just as the curve was approaching this plateau, not with genuinely unbounded growth. This is offered as a well-evidenced **prediction that this pass's own contention-blocked long run could not directly confirm**, not as an observed plateau; what would settle it is a clean run of a few thousand ticks past tick ~1,700 on an uncontended machine.

**Bisection (Design C) - by subtraction on the real app, not from-scratch addition; deviation noted.** Building an additive from-scratch harness (bare `App` -> `DataTable` -> `PriorityTable`) was attempted first: a bare `App` with a paused no-op `set_interval` and no widgets shows **zero** growth of any tracked type over 500 ticks. Adding a plain `DataTable` with 14 rows/6 columns and a per-tick `update_cell()` loop shows `Segment`/`PseudoClasses` growth that **plateaus quickly** (by ~tick 200) rather than growing linearly like the real app - a materially different curve shape from the real app's constant-rate growth through tick 1,000, so this step does not cleanly reproduce the finding and further additive steps would not have isolated it either. Given this, the isolation was instead done **subtractively on the real `LightcycleApp` harness**: individual per-tick calls were monkeypatched to no-ops one at a time and the run repeated for 600 ticks. Disabling `_update_cells` (or the whole `_render_priority_rows`) makes `Segment`/`PseudoClasses` growth **stop completely** (flat for the full 600 ticks). Disabling `_sync_active_glyph_animation` or both `_refresh_backlog_view`/`_refresh_done_view` has **zero effect** - growth continues at exactly the same 108/tick and 1/tick rates as the unmodified baseline. This pins the growth specifically to `PriorityTable`'s own per-tick `table.update_cell()` calls (`app.py:2054-2085`), not to the glyph timer or the (inactive, off-screen) backlog/done views - settling Design C's question via a different method than Design's own from-scratch procedure describes, flagged here per this spec's own instruction to build to Acceptance and note discrepancies from narrative rather than silently reconcile them.

**Referrer tracing (Design D), per type.** For the five types that do not grow in this pass's own run (`Callback`, `Event`, `deque`, `partial`, `set`), a live instance's referrer chain terminates in ordinary framework/stdlib state as noted above - static, not part of this finding. For the two that do grow:

- **`textual.widget.PseudoClasses`**: an arbitrary live instance traces to `BacklogTable._pseudo_class_state` - a _different_, currently non-visible table, whose own `render_lines()` (and thus its own `_pseudo_class_state` reassignment) is never invoked in this harness, consistent with the subtraction result above (backlog/done views contribute nothing to the growth). The actual growth-driving mechanism was pinned by direct cache introspection rather than by chasing an arbitrary gc referrer to its end: every tick, `PriorityTable.render_lines()` assigns a **new** `PseudoClasses` instance to `self._pseudo_class_state` (`_data_table.py:2474-2475`), which then gets embedded as-is into every `_cell_render_cache` key created during that render pass. Old generations' `PseudoClasses` objects stay reachable only via still-live `_cell_render_cache` entries, and are freed once the LRU evicts those entries.
- **`rich.segment.Segment`**: an arbitrary live instance (a Footer key-binding label's own Segment) traces to that widget's own `textual._styles_cache.StylesCache._cache` - a small, properly bounded per-widget line cache, not evidence of the growth itself. The actual growth-driving Segments were pinned the same way as `PseudoClasses`: `_cell_render_cache`'s cached values are `SegmentLines` (lists of rendered `Strip`s, each holding several `Segment`s), so every one of the ~6 new cache entries per tick carries roughly 18 Segments on average (111,197 live Segments / 6,028 cache entries at tick 1,000) - the same cache, the same cache-key defect, driving both types' growth together.

No `LightcycleApp`-owned attribute, list, or dict was found holding either type at any point in either chain; every trace terminates inside Textual's own `DataTable`/`StylesCache` internals.

**Upstream check (Design E).** Network access was available in this pass's execution sandbox (confirmed via a live GitHub API request). Installed Textual is 8.2.8 (`textual.__version__`); GitHub's latest-release API for `Textualize/textual` also returns `v8.2.8` (published 2026-06-30) - the installed version is already current, so no version bump is available regardless of outcome. A search of `Textualize/textual`'s open issues found a related, independently-filed, currently-open memory-retention report: [Textualize/textual#6665](https://github.com/Textualize/textual/issues/6665) ("Memory leak - `StylesCache.get_inner_outer` retains whole `StylesCache` objects via `lru_cache`", filed 2026-07-22), describing `StylesCache.get_inner_outer` decorated `@lru_cache(1024)` as an instance method, so its cache key inadvertently includes the whole `self` (`StylesCache`) instance. This is corroborating-but-not-identical evidence, not a confirmed match: #6665's own reproduction destroys and remounts ~40 widgets per tick (creating many distinct `StylesCache` instances for the cache to pin), whereas `PriorityTable` here is a single, long-lived widget whose own `StylesCache` instance would already be kept alive by the widget itself regardless of this particular `lru_cache`. This pass's own instrumentation points at `DataTable._cell_render_cache`'s own cache-key design as the mechanism actually responsible for the growth measured here (above), with #6665 noted as adjacent evidence that Textual's rendering/caching layer has more than one known, currently-unfixed memory-retention pattern in this version.

**Candidate ceiling (Design F).** From the measured, constant +18.8 KB/tick RSS rate (tick 100-1,000) and the predicted `_cell_render_cache` saturation around tick ~1,662 (above): projecting the same linear rate to that tick gives an estimated **~96 MB** RSS at saturation - closely matching LC-729's own already-recorded ~90-96MB at tick 2,000. Since every cache implicated in this finding is a fixed-size `LRUCache` (`_cell_render_cache` at 10,000; `_row_render_cache`/`_line_cache`/`_row_renderable_cache` at 1,000, already saturated well before tick 1,000), this pass's own reading is that the mechanism itself does not compound further with session length once saturated - so the **same candidate ceiling, ~100 MB, would apply to a full-day (~8,600-tick) session and to a multi-day session alike**, not a larger number for a longer session, provided the underlying mechanism is what this pass's instrumentation says it is. This is a recommendation for the human driver to ratify, not adopted unilaterally, and it rests on the extrapolation above rather than on a directly observed plateau (this pass's own contention-blocked long run could not confirm it directly).

**Recommendation: Textual's own behaviour.** Design D's referrer/cache tracing terminates inside Textual's own `DataTable`/`StylesCache` internals in every case, with no `LightcycleApp`-owned container found holding either growing type at any point - matching Design G's second outcome. The specific, directly-implicated mechanism (`DataTable._cell_render_cache`'s cache key embedding a table-wide monotonic counter and a freshly-constructed `PseudoClasses` instance on every render, guaranteeing a cache miss every tick regardless of content) does not appear to already be the subject of an open upstream report - textual#6665 above is adjacent, not identical - so filing a new upstream issue describing this specific cache-key defect is the recommended follow-up action (the actual filing is a driver action, Out of scope for this item). No version bump is available today (installed = latest, 8.2.8); `pyproject.toml`'s `dependencies = ["textual"]` still carries no exact pin, so if a future Textual release changes this cache's keying, a follow-up item's scope would need to add one to control for it. Separately, on the boundedness question (Design B/F): the evidence assembled here is a strong, mechanistically-grounded **prediction** of a bounded plateau around ~96-100MB, corroborated by LC-729's own already-recorded endpoint, but this pass's own attempt at the direct long-run confirmation Design B calls for was blocked by machine contention rather than resolved - stated plainly, per Design G's own framing, as the one piece this pass leaves for a future clean run to confirm rather than papering over the gap.

## Results ([[LC-788]]'s measurement run, 2026-09-18)

**Setup.** A fresh point-in-time copy of this machine's own live `~/.lightcycle/store.db` (588 items / 3,234 steps total, 134 open/non-done items, counted directly via `sqlite3` on the copy), taken via `sqlite3 .backup` (live store never opened for writing), plus a copy of `~/.lightcycle/workflows`, loaded from an isolated `LC_HOME` built with a real `SqliteStore` against the copy (not `FakeStore`) - the same method [[LC-781]]'s run used, and the live store itself was never pointed at directly. `_refresh()` was driven directly via `TuiSession.poll_tick()`, with the priority tab kept active for every tick (`self._view == "priority"` is this app's own default, unchanged for the whole run). `~/.lightcycle/config` at measurement time: `memory-reserve-fraction: 0.65`, `suspend-pressure: 0.40`, `resume-pressure: 0.25`, `max-agents: 5` - unchanged from [[LC-729]]'s and [[LC-781]]'s snapshots, still meaningfully active, not neutered. This run's build against the live board's own current priority selection found 1 attention row, 5 active rows, 0 queued rows (6 rows/tick total) - the actual row-group composition this measurement's B.2/B.3 findings below are against.

**Design A's own before/after store-call-count claim.** Measured directly, same snapshot, same 20-tick script, run once against this item's Design A fix and once against the unmodified pre-fix `priority_list.py` (`git show origin/main:lightcycle/adapters/tui/priority_list.py`), restored immediately after: `store.children` calls attributable to the per-row rollup were 240 over 20 ticks pre-fix (12/tick, 2 per row) and 120 over 20 ticks post-fix (6/tick, exactly 1 per row) - a directly measured 50% cut in `children` calls alone. Design A also eliminates a `store.get_node` call per row entirely (pre-fix `_rolled_up_cost_text` -> `CostUseCase.execute` -> `self._store.get_node(input.node)`, Sources), which this call-count check does not capture on its own but which is a static, always-true fact of the diff (Sources: `CostUseCase.execute` unconditionally calls `get_node` then `children` for an item node). Combined, this confirms the three-round-trips-per-row-down-to-one claim: 1 `get_node` + 2 `children` (3 calls/row) before, 1 `children` (1 call/row) after.

**B.2: the isolated per-row rollup's share of a visible-priority tick.** Two separate 20-tick `cProfile` runs (sorted `ncalls`, never `cumulative`, per this doc's own method), driven via `TuiSession.poll_tick()` against Design A's fixed code: `_row_for`'s own cumtime was 0.042s and 0.044s (120 calls each = 6 rows x 20 ticks), against `_refresh()`'s own cumtime of 0.276s and 0.296s respectively - **14.9%-15.2% of a tick's `_refresh()` cumtime**, ~2.1-2.2ms/tick in absolute terms (cProfile's own overhead means this absolute figure is a rough order-of-magnitude read, not a trustworthy wall-clock value on its own - the same caution this doc's method section already states - but it is directly comparable to [[LC-729]]'s own ~30ms/tick `DoneUseCase` figure, derived the same way). `store.children` calls: 120/20 = 6/tick, exactly 1 per row (matching B.2's own request and Design A's binding shape) - down from up to 18/tick (3 per row) pre-fix, per the before/after check above.

Compared against [[LC-729]]'s un-isolated 21.8% `build_priority_rows` figure: the isolated rollup alone (14.9%-15.2%) is smaller than that un-isolated figure, as expected once `select_priority_rows`'s own selection work is no longer conflated with the rollup - but that selection work turned out not to be free in wall-clock terms the way Sources row 36's "no `CostUseCase` call, no `store.children()` call" framing might suggest. In this same profiling run, `select_priority_rows`'s own cumtime was 0.173s of `_refresh()`'s 0.276s (62.7%) - the cost is `flow_service.flow_for(node)`, called once per row during selection (`priority_rows.py:29-34`), not any store-call pattern Design A touches. This is a genuine, unexpected finding surfaced by isolating the rollup from selection as B.2 asked, but it is outside this item's own scope (Design A only touches `_row_for`'s store calls; `select_priority_rows`'s `flow_for` cost is untouched by this item's Design) - recorded here, not acted on, the same way this doc has recorded adjacent findings in prior runs.

**B.3: how many rows are provably unchanged, tick to tick.** `_row_for` was instrumented (scratch, not committed) to record each row's owning-node id, group, and resulting `(cost, time)` tuple per tick, across a 30-tick back-to-back run. Post-processing every id present in two consecutive ticks: **174 of 174 consecutive-tick pairs (100%) were unchanged**, broken down by group as 29/29 (100%) attention and 145/145 (100%) active - 0 queued pairs, since this snapshot's own priority selection has 0 queued rows (above).

This 100% figure is not, on its own, the instructive number Design B.3 was looking for, and it would be dishonest to report it without the reason: this run is against a frozen, read-only point-in-time snapshot, with no live worker process attached to mutate the store between ticks. By construction, nothing in a static snapshot can change tick to tick, so a 100%-unchanged reading here is an artifact of the method, not evidence that active/attention rows are structurally unchanging in a real, live session. The genuinely structural question - which rows are _provably_ unchanged, not just coincidentally unchanged in this run - has to be answered by reading the code, not by this snapshot: `select_priority_rows`'s own dedup (`claimed`, `priority_rows.py:23,40-41`) means a queued row's owning item has no step in attention or active for that tick, so no worker session is running against it, and nothing in this codebase records usage or active-seconds for a step that isn't attached to a running session - a queued row's cost/time is therefore genuinely, structurally unchanged for as long as it stays queued, which is exactly the case this item's own brief names. An active or attention row's owning item, by contrast, is exactly the kind of row a real worker could accrue genuine usage or active-seconds against at any moment, so it is never provably unchanged, regardless of what any single snapshot run happens to show.

Read against this run's own row composition, that distinction matters directly: **0 of this board's current 6 priority rows are in the one group (queued, idle) that is actually provably unchanged** - the board's current 6 rows (1 attention, 5 active) are entirely in the group that a cross-tick cache could never safely skip. The case this item's own brief expected to dominate is, on this real board at measurement time, not present in the priority selection at all.

**B.4: recommendation.** Weighed against the reasoning bar this codebase already applied to a materially larger, better-understood case ([[LC-729]]'s "~30ms of CPU work once every 10-second tick - well under 1% of a single core... not a cost that compounds quickly" standard for `DoneUseCase`'s 49.3% share): `_row_for`'s own isolated cost here is ~2.1-2.2ms/tick, roughly an order of magnitude smaller than the cost LC-729 already judged not worth a stateful cache, and Design A has already cut its store round-trips two-thirds (3 to 1 per row) with zero cross-tick risk. Layered on top of that already-small absolute number: (1) no cheap, never-changes-again invalidation key exists for a live Priority row the way `closed_at` does for a Done row (Sources row 31, unchanged by this item's Design A); and (2) on this real board, the one row-group that a cache could safely skip (queued, idle) is currently absent from the priority selection entirely, while the rows that dominate the board (active) are exactly the ones a cache could never safely skip regardless of how the invalidation-key problem were solved. All three considerations point the same direction, so this item lands on:

**Close the cross-tick-caching half of Finding 2 unbuilt.** Design A's dedup fix is this finding's concrete, complete deliverable; no cross-tick cache is built as part of this item (Out of scope), and this measurement is the record for whoever next revisits the question - it would need a live, ticking session (not a frozen snapshot) to get a real fraction-unchanged reading on an active board, and a materially larger absolute cost or a much higher queued-row share than this run found to be worth revisiting the recommendation above.
